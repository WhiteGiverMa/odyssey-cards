# docs 工作约定

> **没有成文的铁律，任何信息冲突以用户最新的表述为准，请提问。**

## 当前策略

从现在开始，`docs/GDD/` 和 `docs/draft/` 不再承担“完成度真相”的职责。

- `docs/draft/`：临时输入池。可以记录需求、对话草稿、审计、临时 TODO，但不要求保持和代码同步。
- `docs/GDD/`：旧整理稿。保留历史上下文，但其中的状态标注可能过期。
- `wiki/`：游戏概念库。重点记录敌人英雄、敌人随从、玩家英雄、武器、技能、卡牌、藏品、关键词、状态、路线房间、奖励与实际 UX 概念；agents 进入前先读 `wiki/AGENTS.md`。

## wiki 口径

wiki 记录“这个游戏概念出现过、它大概是什么意思、目前有哪些来源与待决点”。它不直接等同于现存代码，也不以源码实现为唯一边界。代码层内容可以写，但只作为实现备注，不是 wiki 主轴。

判断规则：

1. **概念存在性**：只要在 GDD、draft、handoff、源码、资源、运行时 UX 中出现过，就可以进入 wiki。
2. **游戏层优先**：优先写卡牌、敌人、玩家、技能、藏品、房间、状态、表现和交互；架构/代码模式只在解释当前状态时附带。
3. **实现状态**：wiki 可以写“已在代码中存在/部分存在/仅设计出现/待决”，但最终有没有、是否好用，以实际游戏 UX 为准。
4. **冲突处理**：新旧表述冲突时，不在 wiki 中强行裁决；先标为“待决/冲突”，后续向设计侧确认。
5. **源码真相**：涉及当前可运行行为时，优先看代码、资源和运行时 QA；旧 GDD 的 ✅/🚧/⬜ 只作为历史信号。
6. **归档**：被本轮或后续整理提取过的 `docs/draft/` 文档，应移动到 `docs/draft/deprecated/`，避免再次把已抽取草稿当成新输入。
7. **代理纪律**：wiki 下的规则只约束 agents，不约束人类；wiki 是概念集，不是准确状态参考。

## 推荐新增流程

- 新游戏概念出现：先写 `wiki/`，哪怕只有一段话。
- 要实现功能：从 `wiki/` 找概念语义，再看代码状态。
- 实现后：更新 wiki 的“当前实现/UX 状态”，而不是回填 draft。
- 发现冲突：在 `wiki/open-questions.md` 或对应条目下记录，集中向用户确认。
- 不因 wiki 形式、预期或旧状态与代码不符而擅自删除；可以随手增写补充。
